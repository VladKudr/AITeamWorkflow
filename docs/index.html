Spec-Driven разработка с ИИ на базе OpenSpec

Единый рабочий цикл для PM, системного аналитика, разработчика и QA: кто какой артефакт создаёт, каким инструментом, кто и по каким критериям принимает. ИИ делает черновики — люди владеют контрактами и решают, что значит «готово».

Зачем это всё

Workflow держится на трёх инженерных принципах. Они определяют, как устроен каждый шаг цикла и каждый гейт этого playbook.

Проверяемость вместо доверия
Качество результата обеспечивается не верой в модель, а дешёвой проверкой: каждый артефакт проходит гейт с чек-листом, спека валидируется командой openspec validate --strict, реализация сверяется с артефактами через /opsx-verify. Проверка встроена в цикл и занимает минуты.
→ Механизм: гейты G0–G6, validate, verify
Полнота — это definition of done
Полнота — свойство критериев приёмки, а не ответа модели. У каждого артефакта есть чек-лист: что обязано быть в спеке, в тест-модели, в design. /opsx-verify меряет полноту против tasks и сценариев — а не «на глаз».
→ Механизм: чек-листы артефактов + verify (completeness)
Интент — от человека, контекст — из спек
PM формулирует бизнес-интент. Технический контекст живёт в main spec (openspec/specs/) и в config.yaml — и подтягивается в каждый промпт автоматически. Никто не диктует модели детали архитектуры руками.
→ Механизм: main spec + context-инъекция config.yaml

Модель работы: ИИ — черновик, человек — владелец

Официальная модель OpenSpec: человек даёт интент и ограничения → агент делает черновик → человек затачивает («draft, sharpen, repeat»). Ни один артефакт не считается готовым, потому что «модель так сказала» — готовым его делает подпись владельца роли на гейте. Аналитик владеет source of truth, который потребляют ИИ-агенты всех остальных ролей; QA определяет качество контракта до того, как написана первая строчка кода; разработчик отвечает за то, что попадает в main.

Как устроен OpenSpec — за 2 минуты

OpenSpec хранит требования не в чатах и не в головах, а в git — рядом с кодом. Две ключевые папки и один цикл.

openspec/specs/Main spec — источник истины.
Как система ведёт себя сейчас
→
openspec/changes/<имя>/Change — предлагаемое изменение:
proposal · specs-дельты · design · tasks
→
Реализацияapply: код пишется по tasks,
спека и код в одной ветке / PR
→
ArchiveДельты вливаются в specs/,
change уходит в архив с датой

После archive main spec снова описывает актуальное поведение — и следующий change строится уже на нём. Спека не устаревает, потому что её обновление — часть цикла, а не отдельная повинность.

Формат спеки: требование + сценарии

openspec/specs/<capability>/spec.md 
## Requirements

### Requirement: Session Timeout
Система SHALL завершать сессию после 30 минут неактивности.

#### Scenario: Idle timeout
- GIVEN аутентифицированная сессия
- WHEN проходит 30 минут без активности
- THEN сессия инвалидируется
- AND пользователь должен пройти аутентификацию заново
Требование — одно наблюдаемое поведение с ключевым словом RFC 2119 (SHALL/MUST — обязательно, SHOULD — рекомендация, MAY — опционально). Тест: сможет ли тестировщик, не видевший кода, сказать, выполняется оно или нет?
Сценарий — конкретный GIVEN/WHEN/THEN, который можно превратить в автотест. Покрывает не только happy path: пустой ввод, просроченный токен, повторный клик. Сценарии спеки — это и есть будущая тестовая модель QA.

Дельты: change описывает разницу, а не всю спеку

Секция дельтыСмыслЧто происходит при archive
## ADDED Requirementsновое поведениедобавляется в main spec
## MODIFIED Requirementsсуществующее поведение меняется (приводится целиком)заменяет старую версию
## REMOVED Requirementsповедение уходит (с причиной)удаляется из main spec
## Purposeназначение новой capabilityстановится Purpose новой спеки
Почему дельты — это важно для команды: два change'а могут менять одну спеку параллельно, не мешая друг другу, пока не трогают одно и то же требование. А если трогают — конфликт при archive это не баг, а сигнал: два изменения по-разному понимают, как должна себя вести система. Разбирает аналитик.

Workflow команды: 9 шагов, 4 роли, 6 гейтов

Один change — одна ветка — один PR. Каждый шаг: кто делает, какой командой, что на выходе, кто принимает. Кастомная схема sdd-roles (см. стартовый пакет) выстраивает артефакты именно в этом порядке.

Прямоугольник — артефакт и команда, которой он создаётся (все команды — /opsx-… в чате GigaCode; подробно — в «Командах простыми словами»). Красный ромб — гейт: контрольная точка с чек-листом (см. «Гейты»). После G6 дельты влиты в main spec — цикл замыкается, следующий change строится уже на обновлённой спеке.

  1. 0

    Интент-бриф PM

    Инструмент: чат-LLM (DeepSeek/Qwen/GLM) по шаблону · CLI не нужен

    PM формулирует: проблема и ценность, для кого, критерии успеха, scope in/out, именованные кейсы («что обидно сломать»), ограничения. Устные и письменные требования не запрещены — они канализируются в бриф. Это единственный новый артефакт для PM.

    Гейт G0 · бриф полон по чек-листу

  2. 1

    Change + Proposal Системный аналитик ИИ — черновик

    Инструмент: GigaCode + OpenSpec
    git switch -c add-payment-limit  ·  /opsx-new add-payment-limit  ·  /opsx-continue

    Аналитик создаёт change и генерирует proposal.md из брифа PM: зачем, что меняем, границы. Ссылка на бриф — обязательна. Один интент — одно предложение; если нужно «а ещё» — это два change'а.

    Гейт G1 · PM подписывает proposal

  3. 2

    Спеки (дельты требований) Системный аналитик ИИ — черновик

    Инструмент: GigaCode + OpenSpec · контекст из main spec подтягивается автоматически
    /opsx-continue  →  правка руками  →  openspec validate add-payment-limit --strict

    ИИ генерирует требования и сценарии, аналитик затачивает: один SHALL на требование, наблюдаемое поведение без деталей реализации, сценарии на негатив и границы. Правильный тип дельты: ADDED / MODIFIED / REMOVED.

    Гейт G2 · validate --strict + QA подтверждает тестируемость сценариев

  4. 3

    Solution design Системный аналитик ИИ — черновик

    Уровень СА: алгоритмы, структуры данных, контракты интеграций — без кода
    /opsx-continue

    solution-design.md — прикладное решение: алгоритмы, модель данных, контракты, нефункциональные ограничения. Именно здесь живёт экспертиза аналитика-архитектора; в код документ не лезет.

    Гейт G3a · ревью техлида/архитектора

  5. 4

    Tech design Разработчик ИИ — черновик

    Требует: specs + solution-design · параллельно QA делает шаг 5
    /opsx-continue

    tech-design.md — перевод solution design на уровень кодовой базы: модули, изменяемые файлы, зависимости. Каждое отклонение от solution design фиксируется явно — это вход для ревью аналитика.

    Гейт G3b · СА проверяет соответствие solution design

  6. 5

    Тест-модель QA ИИ — черновик параллельно с шагом 4

    Требует: только specs — строится из сценариев, НЕ из кода
    /opsx-continue

    test-model.md выводится из сценариев спеки до готовности кода — иначе тесты подтверждают баги, а не требования. Каждый кейс трассируется на Requirement/Scenario; отмечено, что уходит в автотесты. Из этой модели потом генерируются автотесты.

  7. 6

    Tasks + реализация Разработчик ИИ — код

    Инструмент: GigaCode · ИИ пишет код по tasks, разработчик ревьюит каждый diff
    /opsx-continue  →  /opsx-apply  →  git commit → PR

    tasks.md — чек-лист шагов ≤ одной сессии каждый. /opsx-apply ведёт реализацию, отмечая выполненное. В PR попадают и спека, и код — ревьюер читает в порядке: proposal → дельта спеки → код. Узнали новое по ходу — /opsx-update правит план, не наоборот.

    Гейт G4 · code review PR (спека + код вместе)

  8. 7

    Верификация QA Разработчик

    Автотесты из тест-модели + сверка реализации с артефактами
    /opsx-verify  ·  прогон автотестов по test-model.md

    /opsx-verify сверяет реализацию по трём измерениям: completeness (все tasks, требования и сценарии закрыты), correctness (код соответствует интенту спеки), coherence (решения из design отражены в коде). Замечания: CRITICAL / WARNING / SUGGESTION.

    Гейт G5 · 0 critical, warnings разобраны, тест-модель прогнана

  9. 8

    Archive Системный аналитик

    После мерджа PR в main · дельты вливаются в openspec/specs/
    /opsx-archive  или  openspec archive add-payment-limit --yes

    Main spec обновлён, change с полным контекстом (зачем/что/как) уехал в changes/archive/2026-08-11-add-payment-limit/. Через полгода любой сможет понять, почему код выглядит именно так.

    Гейт G6 · только после мерджа · конфликты спек разбирает СА

Право на «лайт»-режим. Опечатка или однострочный фикс не требует шести артефактов — соразмеряйте церемонию с риском. Для тривиальных правок допустим /opsx-ff (все артефакты одним махом) или change c skip_specs: true, если поведение системы не меняется. Полный цикл обязателен для всего, что меняет наблюдаемое поведение, контракты API или данные.

Роли: кто чем владеет

У каждой роли — свой артефакт, свой гейт и своя причина, почему её вес в этом цикле вырос, а не упал.

PM / Владелец продукта

Владелец интента и ценности
Делает
  • Заполняет интент-бриф (единственный новый артефакт)
  • Подписывает proposal на гейте G1: «это та проблема и тот scope»
  • Принимает результат по критериям успеха из брифа
Инструменты
  • Чат-LLM + шаблон брифа. CLI не использует
Смысл роли: ни одно изменение не стартует без ясного «зачем». Бриф PM — корень трассировки всего change'а.

Системный аналитик

Владелец source of truth и прикладного решения
Делает
  • Превращает бриф в proposal, спеки (требования + сценарии) и solution design
  • Держит main spec: archive, разбор конфликтов спек, терминология домена
  • Ревьюит tech design на соответствие solution design (G3b)
Инструменты
  • GigaCode + OpenSpec (opsx-команды, validate)
Смысл роли: спеки аналитика — контракт, который потребляют ИИ-агенты всех остальных ролей. Качество их работы напрямую зависит от качества его артефактов.

Разработчик

Владелец реализации и того, что попадает в main
Делает
  • Tech design: перевод решения на уровень кодовой базы
  • Ведёт /opsx-apply: ИИ пишет код, разработчик ревьюит каждый diff
  • Отвечает за PR: спека + код, зелёные тесты, чистая история
Инструменты
  • GigaCode + OpenSpec, обычный git-flow
Смысл роли: главный навык — инженерное суждение: увидеть, где сгенерированный код разойдётся с системой через полгода. Ревью — это и есть работа.

QA

Владелец качества контракта и финального гейта
Делает
  • На G2 проверяет тестируемость сценариев — до всякого кода
  • Строит тест-модель из спеки (не из кода!), генерирует автотесты
  • Ведёт /opsx-verify и держит гейт G5
Инструменты
  • GigaCode + OpenSpec, тестовый фреймворк команды
Смысл роли: QA смещается в начало цикла — определяет, что значит «работает», когда кода ещё нет. Дешевле всего баг ловится в сценарии спеки.

RACI по артефактам

R — делает (с ИИ-черновиком), A — подписывает/отвечает, C — консультирует, I — информирован.

Работа по шагам: команды по ролям

Что печатать в GigaCode на каждом шаге workflow. Для каждой slash-команды есть CLI-эквивалент — он же используется в скриптах и CI.

Системный аналитик: от брифа до спеки

# ветка под change (имя — kebab-case, один интент)
git switch -c add-payment-limit

# в GigaCode:
/opsx-new add-payment-limit        # каркас change (схема sdd-roles подхватится из config.yaml)
/opsx-continue                     # → proposal.md (даёт ИИ бриф PM как вход!)
#   ...правим proposal, несём PM на подпись (G1)...
/opsx-continue                     # → specs/ — дельты требований со сценариями
#   ...затачиваем требования и сценарии...

# проверка структуры (терминал):
openspec validate add-payment-limit --strict
openspec status --change add-payment-limit   # что готово, что заблокировано

/opsx-continue                     # → solution-design.md (уровень СА, без кода)
Как «аимить» ИИ при генерации спеки: назвать интент и границу («…не трогая существующий API лимитов»), перечислить кейсы, которые важно покрыть, — ИИ покрывает то, на что вы указали. Дальше режим «draft → sharpen»: расплывчатый SHALL уточнить, пустой сценарий удалить, недостающий негативный кейс попросить добавить.

Разработчик: от design до PR

git switch add-payment-limit       # та же ветка, тот же change

/opsx-continue                     # → tech-design.md (требует specs + solution-design)
/opsx-continue                     # → tasks.md — чек-лист реализации
/opsx-apply                        # ИИ реализует по tasks, отмечая выполненное; ревьюим каждый diff

# план разошёлся с реальностью? правим план, а не забиваем:
/opsx-update                       # корректирует артефакты, код не трогает

git add -A && git commit -m "add-payment-limit: spec + implementation"
# открыть PR: в нём и спека, и код. В описание PR — ссылку на change-папку

QA: тест-модель и верификация

# можно начинать сразу после гейта G2 — код не нужен:
/opsx-continue                     # → test-model.md из сценариев спеки
# ...генерация автотестов из тест-модели (GigaCode, по вашему тестовому фреймворку)...

# когда реализация готова:
/opsx-verify                       # completeness / correctness / coherence
# CRITICAL → возврат разработчику; WARNING → разобрать явно

Аналитик: закрытие цикла

# после мерджа PR в main:
/opsx-archive                      # предложит слить дельты в specs/ и заархивирует
# или в терминале/CI:
openspec archive add-payment-limit --yes

Если GigaCode не подхватил slash-команды

Slash-команды — это просто markdown-файлы в .qwen/commands/opsx-*.md. Если ваша сборка GigaCode их не видит, у OpenSpec есть машинный контракт — агенту можно давать инструкции напрямую:

openspec status --change add-payment-limit --json       # какой артефакт следующий
openspec instructions specs --change add-payment-limit --json  # шаблон + контекст + правила для артефакта
openspec instructions apply --change add-payment-limit --json  # контекст и состояние tasks для реализации

Промпт агенту тогда выглядит так: «выполни openspec instructions specs --change … --json и создай артефакт по полученной инструкции». Это тот же механизм, которым пользуются штатные slash-команды.

Гейты: чек-листы приёмки

Гейт проходит артефакт, а не человек и не модель. Не прошёл — возвращается на доработку с описанием дефекта. Чек-лист — это definition of done: именно он делает «полноту» измеримой.

G0Интент-бриф полонПроверяет: СА
  • Проблема и ценность сформулированы; понятно, для кого
  • Критерии успеха измеримы
  • Scope in и scope out указаны явно — «чего НЕ делаем» не менее важно
  • Названы кейсы, которые «обидно сломать»
  • Один интент. Если в брифе «а ещё…» — это второй change
G1Proposal подписанПроверяет: PM
  • Интент proposal совпадает с брифом (ссылка на бриф присутствует)
  • Scope не разъехался: ничего не добавлено «заодно» и не потеряно
  • Затронутые команды/системы и rollback-план указаны
G2Спека принятаПроверяют: СА + QA · автоматика: validate --strict
  • openspec validate <change> --strict проходит без ошибок
  • Каждое требование — одно наблюдаемое поведение, один SHALL/MUST
  • Формулировки — поведение, не реализация («система отклоняет платёж свыше лимита», а не «метод validate() бросает исключение»)
  • У каждого требования ≥ 1 сценарий; негативные и граничные случаи покрыты
  • QA подтверждает: каждый сценарий проверяем тестом
  • Тип дельты верен: ADDED — новое, MODIFIED — изменение (целиком), REMOVED — с причиной
  • Термины — из main spec, новые термины не изобретены без нужды
G3Design принят (a: solution / b: tech)Проверяют: техлид (a) · СА (b)
  • Solution design без кода: алгоритмы, данные, контракты, НФТ-ограничения
  • Tech design ссылается на решения solution design; каждое отклонение зафиксировано явно
  • Ключевые решения оформлены как «Decision + почему» (альтернативы упомянуты)
G4PR принятПроверяет: ревьюер-разработчик
  • PR содержит и спеку, и код; ревью в порядке proposal → дельта → код
  • Код делает ровно то, что в требованиях — не больше и не меньше
  • Все tasks отмечены; тесты зелёные
  • Несогласие с подходом высказано против proposal/design, а не против 300 строк кода
G5Верификация пройденаПроверяет: QA
  • /opsx-verify: 0 CRITICAL; каждый WARNING явно разобран (исправлен или принят с причиной)
  • Автотесты из тест-модели прогнаны; кейсы трассируются на сценарии спеки
  • Расхождение кода и design'а либо исправлено в коде, либо зафиксировано через /opsx-update
G6Archive выполненПроверяет: СА
  • PR смерджен в main — архивируем только вошедшее в продукт
  • Дельты влиты в openspec/specs/; конфликты спек разобраны СА содержательно
  • Change лежит в archive/ с датой; в специфarchive ничего не потеряно

Типовые ситуации

Реализация показала, что план был неверен
Это норма, а не сбой: OpenSpec — «iterative not waterfall». /opsx-update правит планирующие артефакты, сохраняя их согласованность (код не трогает). Правило: код никогда не должен молча расходиться со спекой — либо чиним код, либо обновляем спеку через update, осознанно.
Обновить существующий change или завести новый?
Обновить — если интент тот же: уточнение исполнения, сужение scope (MVP сначала), поправки от изучения кодовой базы. Новый change — если интент изменился, scope разросся в другую работу, или исходный change можно закрыть как самостоятельный. Тест: «можно ли исходный change назвать „сделано" без этих правок?» Если да — новый change.
Два change'а конфликтуют в specs/ при archive
Значит, два изменения по-разному описали одно требование — это фича, а не бага: git подсветил рассогласование о том, как должна вести себя система. Разбирает СА содержательно (какое требование отражает реальность), это обычный merge-конфликт в markdown. Для массового закрытия — /opsx-bulk-archive: он сам находит конфликты и применяет дельты хронологически, сверяясь с тем, что реально реализовано.
Параллельная работа и срочные врезки
Change'и — отдельные папки и ветки, они не мешают друг другу. Прилетел срочный багфикс во время работы над фичей: /opsx-new fix-… → /opsx-ff → /opsx-apply → archive, затем /opsx-apply add-payment-limit — продолжит с места остановки. Правило: один change — один автор; нужно двое — значит, это два change'а.
Изменение не меняет поведение (рефакторинг, инфраструктура)
В .openspec.yaml change'а указать skip_specs: true — валидатор перестанет требовать дельты спек. Proposal и tasks всё равно полезны: «зачем» и «что сделано» остаются в архиве.
Change слишком большой
Признаки: scope в proposal читается как список несвязанных фич; ревью займёт полдня — значит, его никто не сделает; половина tasks может уехать отдельно. Решение: резать по интентам. Маленькие change'и — это быстрые гейты, а быстрые гейты — это доверие к процессу.
Спека и код успели разойтись (легаси-дрейф)
Выборочная сверка: openspec show <spec> --json --requirements, затем агент читает код затронутого модуля и сверяет с требованиями — лучше не той моделью, что вела изменения. Если main spec систематически врёт — это сигнал, что change'и мерджатся без archive: чинить процесс (G6), а не спеку.

Команды простыми словами

Что на самом деле делает каждая команда, когда её набирать и что произойдёт после. Читать перед первым использованием — 10 минут.

Сначала — самое частое недоразумение. У OpenSpec две половины, и работают они в разных местах. Команды openspec … набираются в терминале — как git или npm. Команды /opsx-… набираются в чате GigaCode — там же, где вы обычно пишете агенту «добавь кнопку». Slash-команда — это не программа, а готовая инструкция агенту: «следуй процессу OpenSpec на этом шаге». Начните набирать / в чате — автодополнение покажет список. Если набрать /opsx-propose в терминале — ничего не произойдёт, это нормально.

/opsx-explore — «давай подумаем, ничего не создавая» СА PM

Что делает: свободный разговор с агентом об идее или проблеме. Агент читает код, находит причины, сравнивает варианты решения. Не создаёт ни файлов, ни кода — это безопасный режим «подумать».

Когда набирать: есть проблема, но нет плана. «Поиск подтормаживает, не пойму почему», «как лучше сделать лимиты — на нашей стороне или в процессинге?»

Что дальше: когда из разговора родилась ясность — /opsx-new под конкретное изменение.

/opsx-new имя-изменения — «заведи папку под изменение» СА

Что делает: создаёт каркас change'а — папку openspec/changes/имя/ с метаданными (наша схема sdd-roles подхватится из config.yaml автоматически). Ничего не генерирует — просто заводит место и останавливается.

Когда набирать: начало любой задачи. Имя — kebab-case, один интент: add-payment-limit, а не feature-1 или wip.

Что дальше: /opsx-continue — начнёт создавать артефакты по одному.

/opsx-continue — «сделай следующий артефакт и остановись» СА Dev QA

Что делает: агент смотрит на change: какие артефакты уже есть, какие разблокированы по зависимостям схемы (например, tech-design нельзя делать, пока нет specs и solution-design). Показывает картину, создаёт ровно один следующий артефакт — и останавливается, чтобы вы его отревьюили. Никакого кода, только документы.

Когда набирать: каждый раз, когда ваша роль должна дать свой артефакт. Это главная команда нашего workflow: одна и та же команда у аналитика создаст proposal → specs → solution-design, у разработчика — tech-design → tasks, у QA — test-model. Кто набирает — тот и получает свой шаг; схема сама знает порядок.

Как это выглядит:

Вы:  /opsx-continue
ИИ:  Change: add-payment-limit · схема sdd-roles
     Готово: proposal ✓, specs ✓, solution-design ✓
     Доступно сейчас: tech-design, test-model
     Создаю tech-design.md на основе specs и solution-design…
     Готово — посмотрите и скажите, что поправить.

Что дальше: прочитать, поправить (руками или попросив агента), пройти гейт — и снова /opsx-continue для следующего артефакта. Если артефакт заблокирован — агент скажет, чего не хватает.

/opsx-propose описание — «сделай сразу весь план» СА

Что делает: то же, что new + все continue подряд: создаёт change и все планирующие артефакты одним махом. Быстро, но ревьюить придётся всё сразу — промежуточных остановок нет.

Когда набирать: у нас — для мелких и очевидных изменений, где полный поартефактный цикл избыточен. Для обычных задач — new + continue, чтобы гейты работали.

/opsx-ff — «прокрути планирование до конца» СА Dev

Что делает: fast-forward: несколько continue подряд без остановок — создаёт все оставшиеся планирующие артефакты уже заведённого change'а.

Когда набирать: изменение мелкое и очевидное, а change уже заведён через new. В командной работе по ролям не используется — никто не ревьюит промежуточные шаги.

/opsx-apply — «реализуй по чек-листу» Dev

Что делает: первая команда, которая пишет код. Агент читает tasks.md и выполняет задачи по порядку, отмечая галочки. Контекст берёт из всех артефактов change'а — спека и design уже «в голове» у агента.

Когда набирать: планирование пройдено (для нас: гейты G1–G3 закрыты, tasks.md готов). Прервались — повторный /opsx-apply продолжит с первой неотмеченной задачи, хоть завтра, хоть в новой сессии.

Обязанность разработчика: ревью diff'а после каждой задачи. Agent пишет — вы принимаете решение.

/opsx-update — «план изменился — поправь документы» СА Dev

Что делает: правит планирующие артефакты, сохраняя их согласованность между собой: поменяли требование — агент предложит согласованные правки в design и tasks. Каждую правку подтверждаете. Код не трогает.

Когда набирать: реализация показала, что план был неверен; сузили scope; изменился подход. Правило команды: код никогда не расходится со спекой молча — либо чиним код, либо /opsx-update.

/opsx-verify — «проверь, что сделано ровно то, что написано» QA

Что делает: сверяет реализацию с артефактами по трём измерениям: completeness — все ли tasks, требования и сценарии закрыты; correctness — соответствует ли код интенту спеки; coherence — отражены ли решения design'а в коде. Выдаёт отчёт: CRITICAL / WARNING / SUGGESTION.

Когда набирать: apply завершён, перед архивированием. Сам по себе archive не блокирует — но у нас это гейт G5: 0 critical, warnings разобраны.

/opsx-sync — «перенеси дельты в main spec, не закрывая change» СА

Что делает: вливает дельты спек change'а в openspec/specs/, но сам change оставляет активным.

Когда набирать: отдельно — почти никогда: archive сам предложит sync, если дельты ещё не влиты. Нужен, когда main spec должен обновиться раньше, чем change закроется.

/opsx-archive — «закрой изменение» СА

Что делает: финал цикла. Проверяет, что tasks выполнены (предупредит, если нет), предлагает влить дельты в main spec, переносит папку change'а в changes/archive/2026-08-11-имя/. После этого main spec снова описывает актуальное поведение системы.

Когда набирать: у нас — только после мерджа PR в main (гейт G6). Архивируем то, что реально вошло в продукт.

/opsx-bulk-archive — «закрой несколько изменений разом» СА

Что делает: находит завершённые change'и, проверяет, не трогают ли они одни и те же спеки, разруливает конфликты (сверяясь с тем, что реально реализовано в коде) и архивирует хронологически.

Когда набирать: накопилось несколько смердженных change'ей — например, при еженедельной уборке.

/opsx-onboard — «научи меня на нашем коде» новички

Что делает: интерактивный тур 15–30 минут: агент проводит через полный цикл propose → design → implement → archive на вашей реальной кодовой базе, объясняя каждый шаг. Результат работы — настоящий, его можно оставить.

Когда набирать: первый день каждого члена команды в OpenSpec. Обязательный шаг недели 1 пилота.

Установка и первичная настройка OpenSpec (CLI, openspec init, расширенный профиль команд, стартовый пакет) выполняются по внутренней инструкции. Playbook предполагает, что команды /opsx-… уже доступны в GigaCode, а схема sdd-roles установлена в репозитории.

Демо-проект: цикл в реальности

transfer-limits-demo — мини-сервис внутрибанковских переводов, на котором весь цикл playbook пройден по-настоящему: артефакты созданы по схеме sdd-roles, спеки проверены openspec validate --strict, автотесты написаны из тест-модели, дельта влита в main spec командой openspec archive. Проект поставляется zip-архивом рядом с playbook; внутри — git-история и файл WALKTHROUGH.md с этим же маршрутом. Демо-задача: добавить суточный лимит переводов со счёта.

Четыре точки истории git

1 · Начальное состояние. Сервис переводов до цикла: проверки суммы, валюты, средств; 4 теста.
2 · init + main spec. Подключён OpenSpec, схема sdd-roles; main spec наполнен и подписан СА — сценарий А раздела «Main spec».
3 · PR change'а. Ветка add-daily-transfer-limit: все артефакты + код + тесты одним PR — ревью в порядке proposal → дельта → код.
4 · Archive. Дельта влита: в спеке transfers было 4 требования — стало 5; change целиком уехал в changes/archive/2026-08-11-….

Change «в полёте»: как схема ведёт порядок

Второй change — notify-on-limit-exceeded — намеренно оставлен на середине (готовы proposal и specs). Статус показывает главный механизм схемы: зависимости блокируют артефакты, пока не готовы их входы.

openspec status --change notify-on-limit-exceeded
Schema: sdd-roles
Progress: 2/6 artifacts complete

[x] proposal
[x] specs
[ ] solution-design
[-] tech-design (blocked by: solution-design)
[ ] test-model
[-] tasks (blocked by: tech-design)

Довести этот change до archive — готовое практическое упражнение первого занятия пилота.

Проверить руками — 5 минут

python -m pytest -q                                  # 9 passed
openspec list --specs                                # capability transfers
openspec validate --all --strict                     # всё valid
openspec status --change notify-on-limit-exceeded    # блокировки схемы
git log --oneline --graph                            # change = ветка = PR
Чему учит демо: требование лимита стало частью источника истины только после archive; порядок артефактов держит схема, а не дисциплина; тест-модель выведена из спеки — граничный кейс TC-02 родился из секции брифа «что обидно сломать», а TC-05 закрепил порядок проверок из solution-design; один PR несёт спеку и код вместе, и ревьюеру не приходится восстанавливать замысел по диффу.

Стартовый пакет: скопируй и работай

Четыре файла, которые превращают «голый» OpenSpec в наш ролевой workflow. Кладутся в репозиторий после openspec init (поставляются также отдельным zip-архивом рядом с этим документом). Рядом поставляется и демо-проект transfer-limits-demo — полный цикл playbook, реально пройденный на мини-сервисе переводов: все артефакты, гейты, validate и archive; маршрут — в файле WALKTHROUGH.md внутри.

1 · Кастомная схема workflow

openspec/schemas/sdd-roles/schema.yaml 
name: sdd-roles
version: 1
description: Spec-driven workflow с ролевым разделением PM / СА / Dev / QA

artifacts:
  - id: proposal
    generates: proposal.md
    description: Зачем и что меняем — на основе интент-брифа PM
    template: proposal.md
    instruction: |
      Создай proposal строго на основе интент-брифа PM; ссылка на бриф обязательна.
      Фокус на проблеме и границах scope, не на решении. Один интент — одно предложение.
      Укажи затронутые команды/системы и rollback-план.
    requires: []

  - id: specs
    generates: specs/**/*.md
    description: Дельты требований со сценариями (СА)
    template: specs.md
    instruction: |
      Каждое требование — одно наблюдаемое поведение с SHALL/MUST (RFC 2119).
      Минимум один сценарий GIVEN/WHEN/THEN на требование; негативные и граничные
      случаи обязательны. Формулировки — поведение, без деталей реализации.
      Термины бери из main spec (openspec/specs/), не изобретай новые.
    requires: [proposal]

  - id: solution-design
    generates: solution-design.md
    description: Прикладное решение — алгоритмы, данные, контракты (СА)
    template: solution-design.md
    instruction: |
      Уровень системного анализа: алгоритмы, структуры данных, контракты интеграций,
      нефункциональные ограничения. Без кода, имён классов и файлов.
      Ключевые решения оформляй как "Decision: … / Почему: … / Альтернативы: …".
    requires: [proposal]

  - id: tech-design
    generates: tech-design.md
    description: Техническое решение на уровне кодовой базы (Dev)
    template: tech-design.md
    instruction: |
      Переведи solution-design в термины кодовой базы: модули, изменяемые файлы,
      зависимости, миграции. Каждое отклонение от solution-design фиксируй явно
      в разделе "Отклонения" — это вход для ревью аналитика.
    requires: [specs, solution-design]

  - id: test-model
    generates: test-model.md
    description: Тестовая модель из сценариев спеки (QA)
    template: test-model.md
    instruction: |
      Строй тест-модель ИЗ СЦЕНАРИЕВ specs, не из кода. Каждый тест-кейс
      трассируется на Requirement/Scenario (указывай их заголовки). Помечай
      кейсы для автоматизации и приоритет. Добавь негативные кейсы, если
      сценарии их не покрывают — и предложи дельту в спеку.
    requires: [specs]

  - id: tasks
    generates: tasks.md
    description: Чек-лист реализации (Dev)
    template: tasks.md
    instruction: |
      Иерархический чек-лист (1.1, 1.2, …), каждая задача — не больше одной
      рабочей сессии. Группируй по смыслу. Последняя группа — прогон тестов
      из test-model и обновление документации.
    requires: [tech-design]

apply:
  requires: [tasks]
  tracks: tasks.md
Рядом со схемой лежит папка templates/ — заготовки каждого артефакта (в zip-пакете они уже есть). Проверка: openspec schema validate sdd-roles.

# Тест-модель: <имя change'а>

## Матрица трассировки
| ID | Requirement | Scenario | Тип | Приоритет | Авто |
|----|-------------|----------|-----|-----------|------|
| TC-01 | Session Timeout | Idle timeout | позитив | high | да |
| TC-02 | Session Timeout | Активность на 29-й минуте | граница | high | да |

## Кейсы
### TC-01: <название кейса>
- Requirement/Scenario: <точные заголовки из спеки>
- Предусловия / Шаги / Ожидаемый результат
- Данные: <валидные/граничные значения>

## Пробелы спеки
Кейсы, для которых в спеке нет сценария → предложить СА дельту.

Main spec: два сценария старта

Propose и дельты MODIFIED/REMOVED опираются на main spec — источник истины о текущем поведении системы. От того, есть ли он у продукта, зависит стартовая траектория команды.

Сценарий А · main spec есть

Спеки наполнены заранее — перенесены из существующей документации или восстановлены из кода принятым в команде способом.

  • Перед стартом: openspec validate --specs --all --strict без ошибок; в project.md зафиксирован срез кода (repo@commit), которому соответствуют спеки
  • СА проходит спеки и подписывает их до использования как источника истины — неподписанный baseline источником не является
  • Дальше — полный цикл playbook без оговорок: MODIFIED/REMOVED корректны, конфликты спек между change'ами работают как задумано

Когда выбирать: зрелые системы с распределённым поведением и регуляторикой; команды, где propose ведёт аналитик, не читающий код.

Сценарий Б · main spec нет

Delta-first — официальная модель OpenSpec: спеки нарастают от изменений, каждый change документирует только свой участок.

  • /opsx-explore перед propose обязателен: агент читает код зоны изменения, аналитик проверяет его выводы вопросами
  • Первая дельта в новую capability — ADDED с секцией ## Purpose
  • Прежде чем менять существующее поведение — зафиксировать текущее: в дельте MODIFIED описывается и «как есть», и «как будет», а не только новое
  • Помнить: отсутствие требования в спеке не означает, что поведения нет в системе

Когда выбирать: новые сервисы, небольшие модули, зоны с редкими изменениями.

Сценарии комбинируются по зонам одного продукта. Capability, где сосредоточен роадмап ближайших кварталов или где регуляторика требует полноты, доводите до сценария А заранее; остальное пусть дорастает по сценарию Б. Правило простое: чем горячее зона — тем раньше ей нужен baseline. Для планирования, охватывающего несколько репозиториев, у OpenSpec есть stores (beta) — спеки в отдельном репозитории, подключаемом через references; начинать советуем без них, с одного пилотного репо.

Внедрение: пилот и метрики

Пилот на 4–6 недель

НеделяЧто происходит
1Одна команда-пилот. Разворачивание по внутренней инструкции, стартовый пакет; main spec — по сценарию А или Б (раздел «Main spec»). Каждый проходит /opsx-onboard. Выбираем 2–3 некрупных change'а.
2–4Полный цикл на реальных задачах. Лидер пилота (СА) собирает трение по каждому гейту: что мешает, где чек-лист избыточен, где ИИ систематически мажет — правим rules в config.yaml, а не терпим.
5–6Ретро: метрики до/после, правка playbook по фактам. Решение о масштабировании, пилотная команда становится «носителем» практики для следующих.

Метрики, по которым судим

Скорость и предсказуемость
  • Lead time: бриф → мердж PR
  • Доля change'ей, вернувшихся с гейтов (по каждому гейту отдельно)
  • Доля переделок после G4 (поздние возвраты — самые дорогие)
Качество и доверие
  • CRITICAL/WARNING на verify — тренд по неделям
  • Покрытие: доля сценариев спеки, закрытых автотестами
  • Дефекты, дошедшие до теста/прода, у пилота vs остальных
Чего НЕ мерить: «количество строк кода от ИИ» и «процент сгенерированных артефактов». Эти метрики поощряют объём вместо качества.

Ответственность за ошибки ИИ

Правило одно: за артефакт отвечает тот, кто его подписал на гейте, — независимо от того, кто печатал текст: человек или модель. «Это ИИ так написал» — не аргумент на разборе, как не был аргументом «это Stack Overflow так написал». Именно поэтому гейты обязаны быть дешёвыми: подписывать не глядя — нельзя, а значит, проверка должна занимать минуты, не часы. Чек-листы G0–G6 для этого и существуют.
