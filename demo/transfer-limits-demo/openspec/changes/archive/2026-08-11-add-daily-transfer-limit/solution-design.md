# Solution Design: Суточный лимит переводов

## Алгоритмы
При создании перевода: после существующих проверок (сумма, валюта, средства)
вычислить S = сумма успешных переводов счёта-источника с 00:00 текущих суток
(UTC). Если задан лимит L и S + amount > L — отказ DAILY_LIMIT_EXCEEDED.
Порядок проверок фиксирован: лимит проверяется ПОСЛЕДНИМ, чтобы сообщения об
ошибках не маскировали друг друга.

## Данные
Новых сущностей нет. Расчёт S — по журналу переводов (Transfer.created_at,
Transfer.src_account). Отдельный счётчик не заводим: журнал — источник истины,
двойной учёт исключён.

## Контракты
Публичный интерфейс TransferService расширяется обратно совместимо:
лимит передаётся при создании сервиса, умолчание — «не задан».
Новая ошибка DAILY_LIMIT_EXCEEDED в общей иерархии TransferError.

## Нефункциональные ограничения
Granularность суток — календарные сутки UTC (не «скользящие 24 часа») —
проще объяснить клиенту и воспроизвести в поддержке.

## Решения
### Decision: считать по журналу, а не вести счётчик
Почему: журнал уже есть; счётчик требует синхронизации и обнуления по расписанию.
Альтернативы: Redis-счётчик с TTL — отклонено как лишняя зависимость для демо.
